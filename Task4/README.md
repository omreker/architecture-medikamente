# Оценка узких мест при миграции

## 1. Анализ ситуации

Текущее состояние:

- 1С:Бухгалтерия и 1С:Торговля работают в файловом режиме

- Excel и сканы мед.карт хранятся на общем файловом сервере

- ККМ подключены по TCP/IP + OLE

- Вся инфраструктура на одном физическом сервере

- Ручные процессы, отсутствие автоматизации и аудита

Цели миграции:

- Переход на современную архитектуру (микросервисы / модульный монолит)

- Поддержка пятикратного роста данных и открытия филиалов

- Единая система записи, EMR, платежей и мобильное приложение

- Соответствие 152-ФЗ, 323-ФЗ и принципам Privacy by Design

## 2. Диаграмма Исикавы

Корневая проблема: снижение производительности и стабильности системы при миграции.

### Основные категории причин

| Категория | Возможные причины |
| --- | --- |
| Инфраструктура | Единый физический сервер, отсутствие автоскейлинга, узкие каналы сети, недостаток ресурсов Kubernetes, Windows-зависимости |
| ПО / Архитектура | Переход от монолита к микросервисам, неоптимальные границы сервисов, синхронные вызовы, отсутствие кэширования, технический долг 1С |
| Данные | Грязные Excel и сканы, отсутствие схемы данных, долгая миграция больших объёмов, рассинхрон dual-write, влияние encryption на latency |
| Интеграции | OLE / TCP ККМ, файловый режим 1С, отсутствие API-контрактов, ручной обмен с лабораторией, разные протоколы и форматы |
| Персонал и процессы | Недостаток компетенций, сопротивление изменениям, отсутствие runbooks, ручное тестирование, нечёткие процессы cut-over |
| Безопасность | Encryption замедляет I/O, ABAC добавляет latency, большой объём audit-логов, ошибки настройки ключей, регресс доступа после миграции |

## 3. Рекомендации по устранению узких мест

| Приоритет | Мера | Категория |
| --- | --- | --- |
| P0 | Использовать Strangler Pattern (новые функции только в новом стеке) | Архитектура |
| P0 | Dual-write + reconciliation jobs + feature flags | Данные |
| P0 | Изолировать платёжный контур / ККМ | Интеграции |
| P0 | Capacity planning + load testing до cut-over | Инфраструктура |
| P1 | Чёткие bounded contexts + асинхронные API | Архитектура |
| P1 | Автоматизировать миграцию данных | Данные |
| P1 | Contract testing + mTLS для внешних API | Интеграции |
| P1 | Обучить / нанять DevOps и Security engineer | Персонал |
| P1 | Кэширование + read replicas | Архитектура / Инфра |
| P2 | Постепенное включение field-level encryption | Безопасность |
| P2 | Асинхронный audit (очередь) | Безопасность |
| P2 | Runbooks + chaos engineering + автоматический rollback | Процессы |

## 4. Выводы

Основные источники рисков при миграции:

1. Legacy-интеграции (ККМ, файловый 1С, ручной обмен с лабораторией)

2. Качество и объём данных (Excel + сканы)

3. Недостаток компетенций у небольшой IT-команды

4. Накладные расходы механизмов безопасности (encryption, ABAC, audit)

Системный подход (strangler pattern, dual-write, изоляция критических контуров, раннее load-тестирование) позволяет минимизировать влияние этих узких мест и обеспечить стабильную работу системы уже на этапе MVP.
