# Анализ безопасности системы «Медикаменте»

## 1. Выявление конфиденциальных данных

### Категории данных, которые не учтены

| Категория | Примеры | Где хранятся сейчас | Проблема |
| --- | --- | --- | --- |
| Специальные категории ПДн + врачебная тайна | Диагнозы, анамнез, результаты анализов, назначения | Excel, PDF/JPG | Нет шифрования, нет RBAC, нет аудита |
| Идентификационные ПДн | ФИО, ДР, паспорт, СНИЛС | Excel, файловый сервер | Открытый доступ по AD |
| Контактные данные | Телефон, email, адрес | Excel + Outlook | Пересылка по почте без контроля |
| Факт обращения | Запись к врачу | Журналы | Любой сотрудник с доступом видит данные |
| Платежи | Суммы, способ оплаты | Excel + 1С + ККМ | Двойной учёт, TCP/IP без TLS |
| Локальные копии | Всё вышеперечисленное | ПК сотрудников | Неконтролируемые копии |

## 2. Аудит мер по обеспечению безопасности данных

### 2.1 Соответствие требованиям 152-ФЗ и 323-ФЗ

| Требование | Текущее состояние | Оценка | Риск |
| --- | --- | --- | --- |
| Согласие на обработку специальных категорий ПДн | Отсутствует явная письменная форма для всех случаев | Не соответствует | Высокий |
| Локализация ПДн граждан РФ (ст. 18) | Данные на локальном сервере в здании компании | Соответствует | Низкий |
| Принцип минимизации данных | Собираются избыточные поля (адрес, место работы) без чёткой необходимости | Не соответствует | Средний |
| Контроль доступа (RBAC/ABAC) | Только доменная аутентификация AD. Нет разграничения по ролям на уровне данных | Не соответствует | Критический |
| Аудит действий с данными | Отсутствует. Нет логов «кто, когда, что смотрел/изменил» | Не соответствует | Критический |
| Шифрование at rest | Файловый сервер и 1С в файловом режиме - без шифрования | Не соответствует | Высокий |
| Шифрование in transit | TCP/IP к ККМ, файловый доступ по SMB - без TLS | Не соответствует | Высокий |
| Врачебная тайна (ст. 13 323-ФЗ) | Нет технических барьеров. Любой сотрудник с доступом к общему диску может открыть мед.карту | Не соответствует | Критический |
| Право субъекта на удаление / прекращение обработки | Нет процессов и инструментов | Не соответствует | Высокий |
| Оценка вреда (ст. 18.1) | Не проводилась | Не соответствует | Средний |
| Назначение ответственного за ПДн | Не назначен / не формализовано | Не соответствует | Средний |

### 2.2 Архитектурные проблемы

1. **Единая точка хранения без сегментации** - все файлы (мед.карты, Excel, сканы) на одном файловом сервере.

2. **Отсутствие Data Lineage** - невозможно отследить, откуда пришли данные и куда ушли.

3. **Монолитные 1С в файловом режиме** - сложно масштабировать и контролировать доступ.

4. **Нет разделения доменов данных** (пациенты / финансы / ТМЦ / кадры).

5. **Отсутствие Privacy by Design** - безопасность не заложена в процессы, а добавляется «сверху».

6. **Ручная обработка** - человеческий фактор = основной вектор утечек.

7. **Нет механизмов Data Minimization и обезличивания** для аналитики.

8. **Отсутствие тегирования чувствительных данных**.

### 2.3 Список проблемных зон

| | Проблемная зона | Описание | Последствия | Приоритет |
| --- | --- | --- | --- | --- |
| 1 | Хранение мед.карт в открытом виде | PDF/JPG + Excel на общем диске | Утечка врачебной тайны, штрафы, репутационный ущерб | Критический |
| 2 | Отсутствие RBAC/ABAC | Любой аутентифицированный пользователь AD может получить доступ к файлам | Несанкционированный доступ | Критический |
| 3 | Нет аудита доступа | Невозможно расследовать инциденты | Невозможность доказать соблюдение 152-ФЗ | Критический |
| 4 | Незащищённые каналы передачи | SMB, TCP/IP к ККМ, Outlook | Перехват данных in transit | Высокий |
| 5 | Отсутствие шифрования at rest | Данные на диске сервера в открытом виде | Физический доступ / ransomware | Высокий |
| 6 | Избыточный сбор данных | Собираются поля, не нужные для оказания услуги | Нарушение принципа минимизации | Средний |
| 7 | Ручные процессы и Excel | Дублирование, ошибки, копии на локальных ПК | Потеря целостности и контроля | Высокий |
| 8 | Нет процессов отзыва согласия / удаления | Невозможно выполнить запрос субъекта | Нарушение прав субъекта ПДн | Высокий |
| 9 | Отсутствие тегирования | Нельзя автоматически применять политики защиты | Невозможность автоматизации контроля | Средний |
| 10 | Нет Data Lineage | Непонятно происхождение и путь данных | Сложность compliance и расследований | Средний |

## 3. Рекомендации по улучшению

### 3.1 Список данных и способы для защиты

| Данные | Способ защиты |
| --- | --- |
| ФИО, паспорт, СНИЛС | Field-level AES-256 + tokenisation |
| Телефон, email | Маскирование в UI + шифрование |
| Диагнозы, анализы, анамнез | Шифрование + access control + аудит |
| Платежные данные | Шифрование + PCI-подобная сегментация |
| Факт обращения | Шифрование + минимизация логов |
| Ключи | Vault / KMS + rotation |

### 3.2 Механизм тегирования данных

Предлагаемая модель тегов:

```text
classification: [public, internal, confidential, restricted]
category: [pii.identity, pii.contact, phi.health, financial]
protection: [encrypt_at_rest, encrypt_in_transit, mask_in_ui, tokenize, anonymize, audit_required]
retention: [short, medium, long, legal_hold]
```

Инструменты: Data Catalog (DataHub), OPA/Cerbos, Apache NiFi / Airflow policies, schema registry с аннотациями.

### 3.3 Инструменты, способы и меры обеспечения конфиденциальности данных

Организационные

- Назначение ответственного за ПДн, политика обработки, обучение сотрудников, регулярная DPIA.

Технические

- Шифрование: AES-256 at rest, TLS 1.3 in transit.

- Управление ключами: HashiCorp Vault / Yandex KMS.

- Контроль доступа: RBAC + ABAC.

- Аудит + Data Lineage: ClickHouse / ELK + OpenLineage / DataHub.

- Минимизация и обезличивание данных.

- DLP и сегментация сети (отдельный контур для медицинских данных).

Процессные

- Privacy by Design / by Default.

- Автопроверка релизов на работу с тегированными данными.

- Процедуры выполнения запросов субъектов и инцидент-менеджмент.

### 3.4 Переход к To-Be

1. Выделить домены данных (Patient, Payment, Inventory, HR).

2. Внедрить единый IAM с поддержкой ABAC.

3. Перейти на структурированные хранилища с field-level encryption.

4. Внедрить Data Catalog + Lineage.

5. Построить озеро данных только на обезличенных данных.

6. API Gateway с политиками на основе тегов.

7. Consent management и право на забвение.

8. Автоматический аудит и алерты на аномальный доступ.
